Email Compliance Check — Pipeline Architecture

AI-powered email surveillance for financial institutions. Ingests PDF/Excel emails, analyzes with Azure OpenAI GPT-4o, detects trading violations, stores findings in SQLite + ChromaDB, and surfaces cross-email patterns (quid pro quo, circular trading).

  • Sort all participants (from + to + cc) alphabetically
  • SHA-256 hash of normalized_subject + joined_participants → first 16 chars
  • Deterministic: same conversation always maps to same thread_id
  • is_external_recipient → true if any To address outside INTERNAL_DOMAIN

src/sender_risk.py
Sender Risk Profiling
Computes a 0–100 risk score from historical violation rate, average LLM confidence, and severity weight. Bands: CLEAN / LOW_RISK / ELEVATED / HIGH_RISK. A HIGH_RISK sender's priority score gets a +10% boost.
compute_risk_profile(stats)

src/sender_risk.py — Risk Formula

raw = (non_compliant / total) × 50 + avg_confidence × 30 + normalized_severity × 20 risk_score = min(100, int(raw)) Risk Bands: HIGH_RISK (≥ 70) → priority_score boosted +10% in graph.py ELEVATED (≥ 40) LOW_RISK (≥ 10) CLEAN (< 10)

src/anomaly_detector.py
Volume Spike Detection (Z-Score)
Computes Z-score over the sender's 8-week email history. Flags emails from senders with a sudden volume spike (Z > 2.0 std deviations). Requires ≥3 weeks of data to fire.

src/anomaly_detector.py — Z-Score Logic

z = (current_week_count - mean) / std_dev Conditions: requires ≥ 3 weeks of history threshold: z > 2.0 → is_anomalous = True Output: { is_anomalous: bool, z_score: float, mean_weekly: float, std_weekly: float, reason: str }

STAGE 4 Guardrails — Two-stage output validation & correction
click to expand
src/guardrails.py — Stage 1
GuardrailValidator (Rule-Based)
Validates LLM JSON without a second API call. Checks structure, types, value ranges, category whitelist membership, minimum evidence lines, minimum reasoning length, and a soft hallucination guard that verifies evidence fingerprints appear in the original email body.
GuardrailValidatorvalidate(finding, email_body)

GuardrailValidator — Checks (in order)

  • Required keys present: categories, confidence, evidence, reasoning, is_compliant
  • Types correct: confidence float, categories list, is_compliant bool
  • Confidence in [0.0, 1.0]
  • All categories in VALID_CATEGORIES whitelist (from YAML)
  • Non-compliant findings must have ≥1 evidence line
  • Reasoning must be ≥30 characters
  • Soft hallucination guard: at least one evidence phrase must appear as a substring in the email body

src/guardrails.py — Stage 2
ComplianceVerifier (Second LLM Pass)
Optional second call to Azure OpenAI with the finding for independent verification. The LLM can return "confirmed" (keep original) or "corrected" (update categories/confidence). Adds a verification_note to the finding.
ComplianceVerifierverify(finding, email)

ComplianceVerifier — Two Outcomes

Confirmed
  • Verifier agrees with original finding
  • Original categories + confidence preserved
  • verification_note: "Confirmed."
Corrected
  • Verifier disagrees → updates categories and/or confidence
  • Corrected values replace originals
  • verification_note explains the correction
Output: validated Finding with optional corrections + verification_note → continues to scoring
STAGE 5 Scoring — Priority score, band & alert level
click to expand
src/scoring_engine.py
ScoringEngine
Computes a 0–100 priority score from category base weights, confidence level, and multi-category bonus. Maps score to priority band (CRITICAL/HIGH/MEDIUM/LOW/COMPLIANT) and alert level (HIGH/MEDIUM/LOW).
ScoringEngine(config)score(finding)

src/scoring_engine.py — Scoring Formula

Step 1: Raw score raw = Σ category.base_weight (e.g. market_manip=10 + circular=10 = 20) Step 2: Multipliers if len(categories) ≥ 2: raw × 1.20 (multi-category bonus) if confidence ≥ 0.80: raw × 1.15 (high-confidence bonus) Step 3: Normalize priority_score = min(100, int(raw / max_raw_score × 100)) Priority Bands (score thresholds): CRITICAL ≥ 80 → alert_level HIGH (confidence ≥ 0.80) HIGH ≥ 60 → alert_level MEDIUM (confidence ≥ 0.50) MEDIUM ≥ 40 → alert_level LOW LOW ≥ 0 COMPLIANT (no categories detected)
Output: priority_score · priority_band · alert_level · score_breakdown → augmented onto the finding dict → persisted

STAGE 7 Cross-Pattern Detection — Quid Pro Quo & Circular Trading

Runs after all emails are persisted. Queries the accumulated SQLite data across the entire batch (and all prior batches) to find multi-party patterns invisible at the per-email level.

click to expand
src/quid_pro_quo_detector.py
Quid Pro Quo Detector (Reciprocal Favor)
Finds pairs (A, B) where A sent a flagged email to B AND B sent a flagged email to A within a 30-day rolling window. Filters by bribery / market_manipulation / employee_ethics categories. Verifies cross-addressing: sender1 appears in recipients2 and vice versa.
detect_quid_pro_quo(db_path, days_window=30)

src/quid_pro_quo_detector.py — Detection Logic

  • SQL query: all non-compliant findings with QPQ-relevant categories
  • Self-join on sender/recipient pairs within 30-day window
  • Filter: party_a appears in party_b's recipients AND vice versa
  • Output per alert: pattern, party_a, party_b, email_ids, subjects, severity, avg_confidence, reasoning
  • Severity escalation: CRITICAL if avg_confidence > 0.85
click to expand
src/circular_trading_detector.py
Circular Trading Detector (Graph Cycle Detection)
Builds a directed communication graph from the recipient_network table (only edges with flagged_count ≥ 1 and market_manipulation or circular_trading categories). Runs DFS to find cycles of length 3–6, e.g. A→B→C→A. Deduplicates by lexicographic rotation.
detect_circular_trading(db_path, min_flagged=1, max_cycle_length=6)

src/circular_trading_detector.py — Algorithm

  • Load recipient_network: edges where flagged_count ≥ min_flagged
  • Filter edges: sender must have market_manipulation or circular_trading finding in history
  • Build NetworkX DiGraph (or manual adjacency dict)
  • DFS from each node, track path; if path closes a cycle → emit alert
  • Cycle lengths 3 to max_cycle_length (default 6)
  • Dedup: store cycles with lexicographically smallest node first → avoids A→B→C = C→A→B
  • Alert fields: pattern, participants[], cycle_length, description, severity
Output: qpq_alerts[] · circular_alerts[] → surfaced via /api/patterns on dashboard

Cross-Cutting Concerns

Azure OpenAI Prompt Caching

The compliance_agent system prompt is built once from compliance_matrix.yaml categories (~1024+ tokens). Azure OpenAI automatically caches this prefix on the server side. Repeated calls within the same session skip re-tokenizing the system prompt, reducing latency and cost on large email batches.

ChromaDB Cosine Similarity Search

Every finding is embedded (subject + reasoning + evidence) into ChromaDB with cosine distance metric. The semantic_search(query) API lets compliance officers find similar past violations by natural-language query — e.g. "coordinate buy orders before open" — without needing exact SQL matches.

SQLite Index Strategy

Two composite indices on the main findings table: idx_hlr_thread on (thread_id, created_at) for fast thread history retrieval, and idx_hlr_sender on (sender, is_compliant) for fast sender risk aggregation. Both are read on every email in the pipeline loop.

LangGraph State Machine (Optional Path)

graph.py reimplements the same pipeline as a typed ComplianceState directed graph with 10 nodes. Enables future integration with LangSmith tracing, parallel fan-out of emails, and node-level retries without changes to business logic.

Scoring Multiplier Chain

Scoring applies multipliers in sequence: multi-category bonus (×1.20 if ≥2 categories), high-confidence bonus (×1.15 if confidence ≥0.80), external-recipient flag (×1.10 from config), and finally a +10% boost in graph.py for HIGH_RISK senders. The chain ensures the most dangerous, multi-faceted emails always surface at CRITICAL.

Pattern Detectors are Post-Hoc

QPQ and circular trading detectors never run per-email — they query the accumulated SQLite history after the full batch completes. This means a circular trading ring (A→B→C→A) is detected even if A, B, and C appear in different uploaded files or across different pipeline runs on different days.
