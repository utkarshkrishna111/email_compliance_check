_detect_thread(state, store, internal_domain) — line 51

What it does: Derives a stable, content-based thread_id by hashing the email subject (normalised) plus the sorted set of all participants. This means every email in the same conversation gets the same ID regardless of order.

Also extracts the recipient list and checks whether any recipient's email domain is outside the org (is_external). External emails get a score multiplier applied later.

2 · retrieve_history
_retrieve_history(state, store) — line 60

What it does: Makes three SQLite queries against HistoryStore, then derives two intelligence signals from the results.

Query 1 — thread history: store.get_thread_history(thread_id) fetches all prior findings for this thread. These bodies will be replaced by summaries in the next node.

Query 2 — sender stats: store.get_sender_stats(sender) returns violation rate, average confidence, and category severity for this sender's full history.

Query 3 — weekly volumes: store.get_weekly_volumes(sender) returns per-ISO-week email counts going back across all history.

From query 2 → compute_risk_profile() produces a risk_band (CLEAN / LOW_RISK / ELEVATED / HIGH_RISK) and a 0-100 score.

From query 3 → detect_volume_anomaly() runs a Z-score. If weekly volume spikes beyond 2.0 standard deviations (requires ≥ 3 weeks of history), is_anomalous=True.

Writes to state
thread_history sender_risk volume_anomaly

3 · build_context
_build_context(state) — line 81

What it does: Assembles the extra_context string that will be injected into the LLM prompt alongside the raw email. Three things happen here:

1. Thread summarisation: Calls build_thread_context(thread_history) from context_builder.py. Prior email bodies are swapped out for their cached LLM summaries — a 3-email thread that would be ~380 tokens becomes ~145 tokens (~62% saving).

2. Risk note injection: If sender_risk.risk_score ≥ 40 (ELEVATED or above), a [SENDER RISK PROFILE: HIGH_RISK score=82 — ...] line is appended. This biases the LLM toward closer scrutiny.

3. Anomaly note injection: If volume_anomaly.is_anomalous == True, a [COMMUNICATION ANOMALY: ...] line is appended.

Writes to state
extra_context

5 · guardrail_check
_guardrail_check(state, validator) — line 105 · ROUTER GATE

What it does: Runs pure rule-based validation on the LLM's finding. No LLM call here — this is fast, deterministic logic from guardrails.py.

Checks performed by GuardrailValidator.validate():

# Required fields present (id, categories, confidence, reasoning) # confidence is a float between 0.0 and 1.0 # at least 1 evidence line (from compliance_matrix: min_evidence_lines) # reasoning length >= 30 chars (from compliance_matrix: min_reasoning_length) # category IDs are valid (exist in compliance_matrix.yaml) # soft hallucination guard: no obviously fabricated sender names

If all checks pass → guardrail_issues = [] → router sends to verify.
If any check fails → guardrail_issues = ["reason 1", ...] → router sends to flag_review.

Writes to state

6a · verify
_verify(state, verifier) — line 113

LLM CALL #2. Passes the same email + the first LLM's finding into ComplianceVerifier.verify(). The second LLM pass is asked to confirm or correct the classification. If it disagrees with the first, it overwrites finding.

Reason for two LLM calls: the first call is creative/analytical, the second is a skeptical reviewer. Together they reduce false positives without sacrificing recall.

7 · score
_score(state, engine) — line 134

What it does: Calls ScoringEngine.score() from scoring_engine.py, which reads the compliance_matrix config to compute a 0-100 priority score from the finding's categories.

Score formula: For each detected category, take its base_weight (0-10). Sum across categories. Normalise to 0-100. Then apply multipliers:

# Multipliers (from compliance_matrix.yaml) × 1.20 if 2+ categories detected (multi_category_bonus) × 1.15 if confidence >= 0.80 (high_confidence_bonus) × 1.10 if is_external == True (external_recipient_bonus) # Priority bands: score >= 80 → CRITICAL score >= 60 → HIGH score >= 40 → MEDIUM score >= 0 → LOW

Then two graph-level extras are applied on top of ScoringEngine's output:

# HIGH_RISK sender boost (+10%) if sender_risk["risk_band"] == "HIGH_RISK" and priority_score > 0: priority_score = min(100, priority_score × 1.10) scored["sender_risk_boost"] = True # Volume anomaly flag if volume_anomaly["is_anomalous"]: scored["volume_anomaly_flag"] = True
Writes to state
scored_finding scored_finding.priority_score scored_finding.priority_band scored_finding.alert_level scored_finding.sender_risk_boost? scored_finding.volume_anomaly_flag?

Cross-Pattern Analysis — runs after the full batch

These two detectors operate on the accumulated SQLite history — not on any single email. They find patterns that only become visible once many emails have been processed and persisted.

🤝 Quid Pro Quo Detector quid_pro_quo_detector.py

Finds mutual-favour arrangements that span two separate email threads. No single email reveals this; only the cross-thread pattern does.

1
Query historical_llm_response for all non-compliant findings within days_window (default 30 days).
2
SQL self-join: find pairs where email1 is from A→B and email2 is from B→A.
3
Filter: both emails must involve a QPQ-relevant category (bribery, market_manipulation, or employee_ethics).
4
Verify actual addressing: sender1 is in recipients of email2, and vice versa.
5
De-duplicate: canonical pair key so A↔B and B↔A count as one alert. Severity = CRITICAL if avg_confidence ≥ 0.80.

🔄 Circular Trading Detector circular_trading_detector.py

Finds coordinated round-trip trade schemes (A→B→C→A) by running DFS cycle detection on the recipient communication network.

1
Query recipient_network for edges where flagged_count >= min_flagged (default 1).
2
Verify each edge: at least one underlying email must be flagged for market_manipulation or circular_trading.
3
Build directed adjacency graph: { sender: {recipient, ...}, ... }.
4
DFS from each node. Intermediate nodes constrained to be lexicographically greater than start to avoid duplicates.
5
Record cycles of length 3–max_cycle_length. Severity: CRITICAL for 3-4 participants, HIGH for 5-6.
How to call graph.py directly
from src.graph import build_graph, make_initial_state, run_cross_pattern_analysis

# 1. Build the compiled graph once (expensive — reuse it across emails)
graph = build_graph(
    internal_domain="yourbank.com",
    db_path="result/history.db",
    chroma_path="result/chroma",
    result_dir="result",
)

# 2. Run one email through the full pipeline
result = graph.invoke(make_initial_state(email_dict))
scored = result["scored_finding"]
print(scored["priority_band"], scored["priority_score"])

# 3. After processing the whole batch, run cross-pattern analysis
alerts = run_cross_pattern_analysis("result/history.db")
print(alerts["quid_pro_quo"])
print(alerts["circular_trading"])
Note: main.py (the CLI) does not use graph.py. It calls each module (compliance_agent, guardrails, scoring_engine etc.) directly in a loop. graph.py is the cleaner LangGraph-wired version — both produce identical scored_finding output. The API server's /api/analyse endpoint can use either path.
